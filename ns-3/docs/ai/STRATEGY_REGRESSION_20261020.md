# 采集修改后的策略回归与真实模型核查

日期：2026-10-20。用户要求验证新增采集代码是否破坏原四种策略，尤其神经网络策略，并核查其实际效果是否不差于转发策略。

本记录区分两个问题：同一策略修改前后的行为是否退化，以及不同策略在同一条件下的交付效果。
模型分类准确率、预测目标覆盖率、Interest 满足率和成功 RTT 不是同一个指标，不能相互代替。

**结论：覆盖范围内的12组修改前后配对全部一致，没有发现采集修改造成策略回归。
但圆圈真实模型的三个固定请求计划中，Neural 满足率都低于 VTDF/RTVTDF，
“神经策略交付效果不差于转发策略”的目标尚未达到。**
本轮没有改动研究源码、策略、模型权重或历史实验数据；新增的是验证产物和本记录。

## 版本与隔离方法

- 修改前版本：`b6bff22`。修改后版本：`cc31e88`（本轮开始时工作区干净）。
- 比较对象是同一主项目的两个提交，未使用 `ns-3_old` 代替修改前版本。
- 将旧提交的完整研究模块、三个场景入口和公共入口导出到
  `build/validation/strategy-regression-20261020/baseline/source/`。
  使用旧公开头覆盖层，独立重编全部7个模块源文件和3个入口，避免新旧类布局混用。
- 编译参数来自本机现有 waf `compile_commands.json`，链接复用两提交间没有变化的 ns-3 依赖；
  同时记录源码、依赖库、程序及研究模块哈希，并由 `ldd` 验证基线实际载入隔离的旧模块。
  这是隔离验收用的构建脚本，不替代项目的 waf 管理流程。最多4个编译进程，未 configure。
- 每轮使用独立工作目录和复制的原始 traces，数据输出只落在验证目录，不覆盖历史数据或模型。
  两个版本使用相同路网、种子、策略参数、控制器和模型。
- 基线不具备新 `--experiment-config` 接口，因此主 A/B 使用两个版本共有的旧运行模式；
  新实验模式主动改变请求时序、车辆/路线和排空规则，不可直接与旧默认模式比较后归因于策略回归。

所有本轮证据位于 `build/validation/strategy-regression-20261020/`，下称 `R/`：

- `baseline/build-plan.json`、`baseline/build-report.json`：编译命令、来源、依赖及载入验证。
- `run_legacy_pair.py`：原模式串行运行脚本，`runs/` 内保存逐轮命令、退出码、日志和原始数据。
- `model-audit/audit_circle_model.py`、`model-audit/result.json`：模型与训练来源的可复现只读核查。

## 原模式圆圈的前后对照

原始单车路线，80s，名义40Hz，`RngSeed/RngRun/SUMO/srand` 均为1。
四种策略分别与修改前的同策略配对，不能把策略之间的不同随机发送时刻忽略掉。
下表两版本数值完全相同：

| 策略 | 成功/生成 | 全请求满足率 | 成功请求平均 RTT | 具有完整3s生命周期的满足率 |
|---|---:|---:|---:|---:|
| NoForward | 1535/1719 | 89.2961% | 178.440ms | 1465/1632 = 89.7672% |
| VTDF | 1606/1719 | 93.4264% | 185.729ms | 1532/1632 = 93.8725% |
| RTVTDF | 1608/1719 | 93.5428% | 180.787ms | 1531/1632 = 93.8113% |
| Neural，真实模型 | 1585/1719 | 92.2048% | 178.622ms | 1513/1632 = 92.7083% |

全请求口径包含车辆结束时尚未完成的请求；完整生命周期子集只选发送至该车辆实际停止
至少还有3s的请求，防止把尾部未排空误当完整超时。两种口径均保留，成功 RTT 仅由 DATA 回调计算，
没有把旧 RTT CSV 中的 TIMEOUT 混入平均值。

Neural 的1711次推理概率输出逐行相同；四策略各自的逐事件协议日志、
训练 CSV、RTT CSV、车辆统计和 L3 tracer 在两版本间一致。
Neural 有1711个 Router 回传请求，其中4个没有有效的当前关联 RSU；
其余1707个中，1702个预测目标集合覆盖当时的关联 RSU（99.7071%）。
这个条件覆盖率既不是全请求分类准确率，也不是满足率，4个关联未知/失联请求没有被算成预测正确。
满足率略低于转发策略的现象在修改前已经存在；成功 RTT 更低也不能抵消丢失更多请求的事实。

## 性能保证的代码边界

当前 Neural 在 `VndnRsu::OnVehicleData` 中依赖预测 RSU 的预备 PIT 自动回程；
不会自动进入 VTDF/RTVTDF 的事后补救分支。选路最多两个候选，
所以实现没有“神经预测失误后必然达到转发策略效果”的下界保证。
这个行为在修改前已存在。

若实际结果未满足用户提出的性能目标，需要进一步核查训练/在线输入一致性、预测目标和回程交付链，
不能通过更换统计分母、删除超时、挑选最好种子或将测试控制器当真实模型来达到目标。

## 修改前神经策略的交付诊断

旧版本圆圈真实模型运行共有119次 TIMEOUT，按请求名称、车辆关联变更和 Router/RSU 日志追踪：

| 超时请求到达的阶段 | 数量 |
|---|---:|
| Router 目标覆盖当前关联 RSU，且 RSU Data 回调时车辆仍关联该 RSU | 107 |
| Router 时覆盖，但到达 RSU 前车辆已经切换 | 2 |
| Router 返回时目标不覆盖当前关联 RSU | 3 |
| 没有 Router 返回 Data 的日志 | 7 |

因此不能将全部超时解释成模型预测错误。107例都有对应无线 Face 257 的预备 PIT 日志，
预备至 RSU Data 回调间隔为120.657–121.669ms，小于3s Interest 寿命。
只读检查未发现选择条件丢失、应用/无线 in-record 相互覆盖或明显寿命换算错误，
但这不证明运行态 PIT 必然正确，也未定位到具体无线丢包原因。

例如 `%FE%16` 在2.770629200s预备 PIT，2.871456801s由 Router 发往 RSU1，
2.892296721s触发 RSU1 Data 回调；期间车辆仍关联 RSU1，最后在5.728664000s超时。
RSU 日志“由 PIT 自动转发”只说明应用收到了回调，不证明无线发送或 OBU 接收成功。

`model-audit/delivery-diagnosis.json` 保存119条分类和三组完整时间线、日志行号、输入哈希；
`delivery-static-review.json` 保存相关源码位置和边界。
旧模式下不同策略会改变全局随机数消耗，即使同名请求的发送时刻也可能不同；
跨策略时间线只能说明各自机制，不能充当同一请求条件下的反事实。
下一步应优先在固定请求计划下关联已有 `packet-l3.csv`、`data-rx.csv` 和请求账本，
区分“RSU 无线出口无 Data”“已有出口但 OBU 未收到”“OBU 收到但应用未满足”。
不能仅凭上述日志修改模型或底层。
