用户最新选择：**优先成功率达到或超过RTVTDF，并改善交接时延；本轮先诊断实现，不增加统计指标。**

现有主图仍按原定义解释。下面的共同请求与路径分段计算仅用于定位实现，不作为新论文指标替换原图。

## 1. 总判断

有值得验证的实现改进空间，但不能保证五项指标同时领先。
圆圈的高时延已能定位到无线L3提交之后的交付阶段，不能靠换平均方法消除。
“不再转发大业务Data”支持低网络负载和较少额外Data提交，不意味着控制负载必然最低。
当前RTVTDF能直接读取仿真车辆实时位置，其定位通信成本未建模；本方案需要实际发送回程控制消息。

本次每条件只有两个种子，不能把微小差异断言为随机误差或显著优势。

## 3. 成功样本偏差不足以解释圆圈时延

circle基准（10车、30km/h设置、6000请求），原图数值：

| 策略 | ISR | 成功RTT |
|---|---:|---:|
| Naive | 34.78% | 183.83ms |
| VTDF | 69.75% | 220.93ms |
| RTVTDF | 83.28% | 440.71ms |
| Neural | 80.22% | 477.41ms |

Naive的低RTT不表示交付最好：约65%请求失败，不进入成功RTT均值。
但我们又按种子及request_id取四策略**全部成功的2922个相同请求**，均值仍为：
Naive182.60、VTDF204.40、RTVTDF384.14、Neural425.43ms。
因此圆圈差距不是仅由幸存样本集合不同造成。

分别两两匹配时，NN与Naive共同成功3758个请求，NN平均多256.23ms；
与VTDF共同成功7082个，多249.98ms；与RTVTDF共同成功8565个，多41.47ms。
这是同请求描述性诊断，不能将包数当作独立实验重复，也不孤立证明某条协议机制的因果贡献。

方阵/蜘蛛网并非同样的全面高RTT：基准原图NN分别316.90/301.66ms，RTVTDF343.39/317.56ms。
不同场景须分别解释，不能把圆圈问题推广为模型在所有场景都更慢。

## 4. 额外延迟已定位到无线提交之后

以下间隔为：目标OBU完整Data接收时间，减去该请求最近一次RSU无线Face的L3 Data出站时间。
这是末跳交付段，**不是直接测量的MAC队列驻留时间**；多站提交取最近一次，具体计数保存在诊断JSON。

| circle条件 | Naive，种子52001/52002 | VTDF | RTVTDF | Neural |
|---|---:|---:|---:|---:|
| 基准，6000请求 | 18.52/17.63ms | 50.82/41.62ms | 247.48/235.94ms | 281.53/281.67ms |
| 12000请求 | 43.43/41.19ms | 207.72/254.52ms | 472.10/466.88ms | 470.79/466.75ms |

NN高请求量时，95.86%–97.13%的成功请求该段超过400ms，P95约501ms。
NN成功请求中，RSU收到Router Data至L3无线提交的平均间隔为0ms。
这把数百毫秒定位在下层无线交付阶段，而非RSU应用拿到Data之后固定等一个定时器。

具体可复核例子：circle/baseline/52001/策略3，`exp-00002:5`：
发送20.810165600s，RSU0收到并无线提交20.980094639s，OBU4接收21.478330162s；
末跳498.235523ms，总RTT668.164562ms。来源是该run的request-events.csv、packet-l3.csv和data-rx.csv。

### 对应的代码事实

- [WiFi队列](../../src/wifi/model/wifi-mac-queue.cc:42)：默认500包、MaxDelay=500ms、满队丢新；本场景未覆盖。
- [WiFi配置](../../contrib/ndn4ivc/helper/wifi-setup-helper.cc:98)：非QoS OCB；每设备各自共享发送队列，不是全网一个队列。
- [Txop](../../src/wifi/model/txop.cc:479)：取队首；广播不等ACK，单播等ACK并可能重试。不可达车辆可能阻塞后续其他车辆/Hello，具体因果尚待MAC轨迹验证。
- [神经回程标签](../../contrib/vndn-nn-rd/apps/vndn-router.cc:271)明确给OBU目标MAC；[传输](../../src/ndnSIM/model/ndn-net-device-transport.cpp:133)按目标单播，且所有LP分片保留目标。
  Naive无目标标签的原生Data通常走广播，VTDF正常应用回传也单播；不能只用广播/单播区别解释NN相对VTDF的差距。
- [物理速率](../../contrib/ndn4ivc/helper/wifi-setup-helper.h:36)为6Mbps，圆圈[业务载荷](../../scratch/vndn-circle-simulator/vndn-circle-main.cc:427)为10240字节。
  12000请求/120秒对应100请求每秒，仅一次Data载荷合计就为8.192Mbit/s，尚不计Hello、分片、ACK和退避。
  所有设备同SCH1；但跨设备合计不是单链路实测利用率，空间复用与实际竞争域仍需核对。
- 原始四策略无线L3业务Data长度都约10292–10294字节，没有发现NN把单包放大的证据。
- [Gym同步动作](../../src/opengym/model/opengym_interface.cc:283)没有把推理墙钟耗时调度为仿真时延；不能把现实Python推理慢直接当作这些RTT的原因。

综合证据强烈指向无线排队/竞争/重试压力，**尚未直接观测每包入队、重试、过期丢弃，不能写为已确认具体MAC根因**。
RTVTDF也到达近500ms边界，说明问题不只是NN独有的推理误差。

## 5. 控制成本为什么不能按期望直接变低

基准条件控制负载，单位Mbit/轮，取两种子均值：

| 场景/策略 | Hello | search+find | neural-route | neural-pit | 总控制 |
|---|---:|---:|---:|---:|---:|
| Circle/VTDF | 124.224 | 7.623 | 0 | 0 | 131.847 |
| Circle/RTVTDF | 118.521 | 0 | 0 | 0 | 118.521 |
| Circle/NN | 116.617 | 0 | 4.009 | 5.323 | 125.950 |
| Grid/RTVTDF | 130.789 | 0 | 0 | 0 | 130.789 |
| Grid/NN | 131.904 | 0 | 3.839 | 5.288 | 141.030 |
| Spider/RTVTDF | 100.456 | 0 | 0 | 0 | 100.456 |
| Spider/NN | 101.698 | 0 | 2.514 | 3.362 | 107.574 |

此窗口内handshake为0。Hello不是各策略必然相同的常数，回复数和携带内容随无线接收/缓存状态变化。
NN控制没有重复发送10×6历史：route平均约85字节，pit约112字节；特征历史走本机Gym接口。
Circle每轮约5875条route和5955条pit，未发现同名控制重复发送。

[RTVTDF定位实现](../../contrib/vndn-nn-rd/apps/vndn-rsu.cc:688)直接读取TraCI车辆位置和RSU坐标，选最近站，没有发送定位查询。
这一假设早于本批次。现有说明仅称“仓库实现”，未证明完全复现原论文，也未预先明确定义为oracle基线。
应如实说明其信息可用性；不能给已完成数据追溯添加虚构定位开销或延迟。

当前route和pit有正确性用途：
[源RSU](../../contrib/vndn-nn-rd/apps/vndn-rsu.cc:754)先删除原无线PIT；
[独立route](../../contrib/vndn-nn-rd/apps/vndn-rsu.cc:782)防止默认转发先行/PIT聚合吞掉带预测标签的代理Interest；
[Router](../../contrib/vndn-nn-rd/apps/vndn-router.cc:349)已经按每请求每目标去重pit。
因此不能因为“车辆目标站没变”就省掉后续请求的PIT，也不能简单删route来让控制图降低。

## 6. 值得验证的优化方向，按优先级排列

1. **先确认无线排队/重试来源。** 使用同一circle输入和种子，跟踪已有慢请求的入队、出队、目的MAC、ACK失败、过期与丢弃。
   区分总体业务超过无线承载能力，还是错站/失联车辆/双路副本导致队首阻塞；保留四策略相同链路条件。
   可以使用明确标记为诊断的正确单目标控制器隔离模型误差，但该结果不能混作本方案性能。
2. **低风险候选：压缩Hello的空白，而非降低观测频率。** [OBU](../../contrib/vndn-nn-rd/apps/vndn-obu.cc:314)使用`j.dump(4)`发送漂亮格式JSON。
   可研究改为紧凑JSON并保证字段/值相同，四策略共享实现一并修改，减少无信息空白。
   先测试解码语义、车辆状态、模型输入不变，再小规模验证ISR/RTT和控制字节，不能从旧表估减后当作新实验。
   当前20ms Hello、40ms失联判定相互耦合，直接降低频率还会改变10步历史，不是等价改动。
3. **核查预测时点与信息新鲜度。** 当前目标是Data回到源RSU时的服务站；若随后还排队约500ms，车辆可能再次移动/换站。
   当前六维序列没有显式历史年龄/无线队列信息；旧历史在超时清理时未同步清空。
   这构成合理的失配假设，但需要关联实际选站、Hello时间及最终交付/丢失，不能凭离线准确率或这段代码就判定根因。
4. **独立排查神经备用回调的身份错误。** Router标签sender是RSU，
   [OnNeuralReturnData](../../contrib/vndn-nn-rd/apps/vndn-rsu.cc:1038)却按OBU解释，可能将Data存入永远等不到对应车辆Hello的缓存，且缓存缺少过期清理。
   应先单测/短程验证并明确唯一交付路径，防止修正身份后触发重复无线发送。
   正常无线PIT已在该回调前发送，所以不能把这个问题直接当作主路径500ms等待的原因。
5. **有证据后再改路由/控制设计。** 如确认错误候选/双路显著增加无效重试，再在独立验证数据上校准阈值、置信处理或交接补救。
   任何控制合并都需验证Interest先到/指令先到/快速回程/同名聚合/过期交接，不能以较少字节替代交付正确性。

不建议先缩短500ms队列寿命：它可能只让困难包更早丢弃，使成功RTT下降而ISR更差。
不建议只给NN提速、减少载荷或降低负载来宣称同条件更优；公共链路/业务设置的变动应四策略一致并明确另一个条件。
旧192轮已经用于此次探索诊断；未来若依据这些结果改算法，最终性能验证应使用未参与选择的新种子。
