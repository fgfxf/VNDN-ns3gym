## 1. 研究问题与已确认口径

研究目标：在业务请求增长、车辆移动加快、车辆规模扩大的条件下，比较不同回程策略的交付可靠性、成功请求时延、额外 Data 副本及通信成本。结论应回答“以多少额外网络资源换取多少交付收益”，不预先规定本方案必须在每项指标上最优。

用户在本轮明确：

1. Interest 数量指**固定测量时段内，全网首次生成的业务 Interest 总数**，不含控制、逐跳转发和重传。
2. 车辆数量主实验保持**每车发包频率不变**；另做固定全网请求量的补充实验，分离车辆密度与总业务量变化。
3. 控制负载指**超出原有 NDN 设计的自定义控制类报文**，按代码判断。此补充说明扩展了导师原话中的 search/find/update 范围；不能继续只统计这三个名称。
4. **所有额外业务 Data 副本都计入二次转发**，包括预测双路径副本和事后跨站补救，内部保留分项。
5. 网络/控制负载主图展示累计发送字节量，换算为 **Mbit（8×bytes/10⁶）**；附表报告每个首次业务请求的字节成本。

下文的参数水平、重复次数和实现接口是根据代码核查提出的方案，不是已经执行的设置，也不是文献通用标准。控制报文与混合业务封装的具体分类见第 5 节。

## 3. 自变量、候选水平及混杂控制

### 3.1 Interest 数量：请求负载实验

横轴：`Number of generated Interest packets`，记为 K。固定车辆数 N₀、速度设置 v₀、轨迹和测量时间 T；为每次重复预生成恰好 K 个业务请求的发送计划，各车均衡分配，在测量窗内铺开，给车辆设置不同相位，避免同一时刻集中爆发。

候选水平为 `0.25K₀、0.5K₀、K₀、1.5K₀、2K₀`，取可均衡分配的整数。四算法重放同一份计划，横轴以**实际首次生成数**核对预算。不得通过延长仿真来增加 K；无驻留 RSU 时已生成但失败的请求仍计入分母，不能只留下有覆盖时的发包。

当前 `--obu-frequency` 是名义频率，实际间隔为 `floor(10⁶/f)+U{0,…,19999}` 微秒；40 Hz 在忽略边界时平均约 28.57 次/秒。精确 K 扫描需新增请求预算/计划入口，不能把 `N×f×T` 当实测数量。**`--i` 实际控制 TraCI 同步间隔，不能拿来调业务发包量**。

### 3.2 车辆速度：移动性实验

横轴建议写 `Vehicle speed setting (km/h)`，候选 `10、20、30、40、50 km/h`。固定 N₀、T、K₀、请求时刻表和路线族，改变车辆速度设置；每个速度水平内部的四算法共享移动输入。

SUMO 实际速度受道路限速、车辆上限、跟驰、路口、加减速和拥堵共同影响，不能把 `maxSpeed` 直接当作实测速度。主图横轴说明是设置值，附表给出测量窗内车辆时间加权平均速度、分位数、停车比例与实际交接数；若实际速度水平无法区分，应在预实验修改设计或如实报告。[SUMO 速度文档](https://sumo.dlr.de/docs/Simulation/VehicleSpeed.html)

当前方阵/蜘蛛网普通车道限速 13.89 m/s（约 50 km/h）；圆圈车辆和普通车道配置为 **100 m/s，而非 100 km/h**。因此不沿用原默认速度做共同基准。预实验可在独立配置中令 `speedFactor=1、speedDev=0` 便于解释速度处理，保留并记录跟驰模型；另做速度异质性敏感性分析。具体参数兼容性须以本地 SUMO 版本核验，不照搬最新文档中的新增字段。

### 3.3 车辆数量：规模与业务量联合增长实验

横轴：`Number of vehicles`，指整个测量窗内持续存在、均产生业务请求的车辆数 N，不是“曾经入场的车辆累计数”。候选 `5、10、20、30、40` 辆；固定每车业务强度 λ₀、T、速度设置、道路与路线分布，因此全网请求量约为 `Nλ₀T`。

论文应将这组结果解释为**车辆规模及总业务量共同增长的承载表现**，不能解释为纯密度效应。补充固定全网 K₀ 的车辆数扫描：将每车请求数量调整为约 `K₀/N`，用于分离交通密度、无线竞争与业务量的作用。两套图分别标注，不混合数据。

圆圈若在最高水平形成持续堵塞，应在独立预实验阶段决定是否采用场景专用水平，例如 `1、5、10、15、20`；正式实验必须披露水平不同。拥堵也可以是有意义的工况，不能看到本方案效果不好后删除或重抽。

### 3.4 一个可核算的预实验起点

以下数字只是开始验证设计的例子：`N₀=10，v₀=30 km/h，λ₀=5 次/车/秒，T=300 s`，则 `K₀=15000`。请求量水平为 `3750、7500、15000、22500、30000`；车辆数扫描的请求预算为 `7500、15000、30000、45000、60000`。请求计划控制真实发包数量，不直接采用存在抖动的现有 5 Hz 参数来保证这些等式。

预实验须检查该范围是否覆盖可区分的移动/负载条件、计算成本是否可承受；若所有负载水平都过轻，或最高水平无法正常运行，应在正式实验前统一调整并冻结，不按算法排名挑选取值。

### 3.5 时长与路线不能直接沿用旧默认值

当前默认圆圈/方阵/蜘蛛网分别为 1/2/20 辆、80/230/230 秒。道路几何只读检查表明：圆圈一圈普通路段约 442 m，10 km/h 自由流行驶一圈约 159 秒；蜘蛛网现有短路线约 166–693 m，在 50 km/h 下普通路段行驶约 12–50 秒就可能结束。上述估计忽略路口、加减速和无线行为，**不是实际交接预测**。

以 `T=200、300、600 s` 为候选，在独立预实验中检查低速及高密度的实际移动、驻留、失联和交接覆盖，再冻结 T。优先全场景共用 T；确需场景专用 T 时，必须在图注标明，只做各场景内部算法比较，不用绝对流量跨场景排名。同一场景所有横轴水平与算法保持相同 T。

必须生成足够长的循环/往返路线，保证测量及收尾期间车辆持续在场。可将“多数车辆经历多次交接”作为预先设置的覆盖检查；例如至少 80% 车辆有两次站间切换是**设计目标**，不是统计充分性的定理，也不能作为正式结果事后删选条件。

方阵原两车走同一底边往返路线，不能只复制它们就声称覆盖全部七基站。预实验应检查路线族、RSU 到访计数和交接矩阵；训练集覆盖正式测试涉及的基站类别，测试轨迹/种子保持独立。

## 4. 统一时间窗口、请求集合与五项指标

### 4.1 请求集合与统计边界

预热期间只建立驻留/发现等基础状态；正式业务请求在 `[t₀,t₁)` 生成，`T=t₁−t₀`。集合 Q 包含该区间内首次生成的全部业务请求，唯一键为 `(run_id, vehicle_id, sequence)`，同时保存完整业务 Name。

每个请求采用相同截止期 `deadline=t_send+3 s`，对应当前 InterestLifetime；重复 Data 只允许首次有效到达满足一次。`t₁` 后停止生成新业务，但继续移动、接收、控制和转发至 `t₂=t₁+3 s+ε`，ε 可先取 0.5 s 并在预实验冻结。控制/网络成本统一累计 `[t₀,t₂)`，**包括固定收尾段**；预热成本另表记录。

不能把现有 `StopApplication()` 当作停止发包：它会关闭 face、清理未决请求。需要独立的“停止新请求”接口。车辆提前离场、Nack、超时、失联不能从 Q 删除：预先计划为持续在线的实验出现轨迹提前结束时，要记录设计/运行问题；真实协议交付失败必须保留。崩溃导致无法确定结果的 run 属于不完整运行，不伪造为协议超时。

### 4.2 指标定义表

设 S 为 Q 中截止时间内首次收到有效业务 Data 的请求集合，L(q) 为其成功 RTT；E 为 `[t₀,t₂)` 内统一网络发送统计点记录的发送事件；b(e) 为该事件字节长度。

| 指标 | 单轮定义 | 推荐英文轴标题 | 解读边界 |
|---|---|---|---|
| 二次转发/额外 Data 副本数 | `N_extra = Σq [主动新增分支 + 补救再投递 + 其他额外同层副本]` | `Number of additional Data copies` | 合并用户要求的全部额外副本，保留原因分项；不是所有普通多跳 Data 发送之和 |
| 兴趣包满足率 | `ISR = 100 × |S| / |Q|` | `Interest satisfaction rate (%)` | 分母含全部首次业务请求；不包含控制 Interest、逐跳转发或重复 Data |
| 平均成功 RTT | `mean RTT = Σq∈S L(q) / |S|` | `Mean RTT of satisfied Interests (ms)` | 只统计成功；没有成功时 NA；不得把超时填为 3000 ms 混算 |
| 网络负载 | `B_net = Σe∈E b(e)`，图值 `8 B_net / 10⁶` | `Network overhead (Mbit)` | 图注定义为全网累计协议发送量，包含正常业务，不是相对某理想基线的额外量 |
| 控制负载 | `B_ctrl = Σe∈E, class(e)∈C b(e)`，图值 `8 B_ctrl / 10⁶` | `Custom control overhead (Mbit)` | C 为第 5 节全部自定义纯控制类别，不只 search/find/update |

网络指标更严格的名称是 `Aggregate network traffic (Mbit)`；如按导师用词保留 `Network overhead`，必须使用上表定义，不把它写成“净额外流量”。平均 RTT 必须与 ISR 一起解释：低成功率算法可能只留下容易成功的请求，呈现较低的条件 RTT。

RTT 使用**模拟时间**。当前 Gym 同步等待 Python 回复后立即继续转发，没有将推理/进程通信的墙钟耗时显式调度为模拟延迟；宿主机 Gym 通信和离线训练也不经过模拟网络，不计入 B_net。论文不能据此声称已评估部署计算时延；可另测固定硬件上的推理耗时，并另设显式推理延迟敏感性实验。源码依据为 RSU 1115–1116、1243–1244 行及 OpenGymInterface 的同步收发实现。

附表同时报告 `N_extra/|Q|`、每千请求副本数、`B_net/|Q|`、`B_ctrl/|Q|`（bytes/Interest），以及可选 `B_net/|S|`（bytes/satisfied Interest）。分母为零时为 NA。成功率改善应优先以**百分点差**报告；副本、成本为零的基线不计算百分比下降率。

### 4.3 额外 Data 副本的计数规则

“副本”按逻辑交付分支/再投递事件识别，保留 `copy_id、parent_copy_id、reason`；第一条正常交付链为主副本。复制身份应随普通转发、缓存等待、封装和解封装关联，不能用函数调用数或每跳新建 packet 对象数代替。

测量标记优先通过旁路日志或不进入线包的仿真元数据关联，避免为了计数而改变协议及字节成本；若必须修改线上编码，须明确记为协议变化并计入发送长度。

| 事件 | N_extra 增量 | 网络字节计数 |
|---|---:|---|
| Server→Router→一个 RSU→OBU 正常回程 | 0 | 各实际网络出口发送分别计入 |
| 预测首次返回实际分给 k 个 RSU | `max(k−1,0)` | 所有分支发送均计入 |
| 单目标预测直接送到新的 RSU | 0 | 正常回程发送计入 |
| 原 RSU 收到 Data 后，经 Router 再送目标 RSU | 每个新的补救再投递副本 +1 | 跨站各跳及后续无线交付分别计入 |
| 上述补救封装经过 Router、目标解封装后发车 | 0；继承该副本身份 | 不漏掉各跳，且不把同一线包的内外载荷重复相加 |
| 同副本只是在队列中等待，之后首次发给车辆 | 0 | 实际发送时计入 |
| 已发出的业务 Data 又产生一次同层重复响应/再投递 | 每新增副本 +1，原因记 `other` 或对应补救原因 | 全部计入 |
| Wi-Fi MAC 重试、hello 响应等控制 Data | 不属于业务 Data 副本指标 | MAC 重试不在所选协议层总量内；控制消息进入控制/网络量 |

业务请求 q 的普通多跳链路经过三跳仍是主副本；预测双路径额外一份是 +1，之后其中一路再跨站补救一份则合计 +2。同一请求最终只满足一次。没有被网络设备接受的发送尝试另记失败尝试，不伪造为已经提交的副本。

当前 Router 双目标回程、RSU `ForwardDataToRsu`、等待队列投递、NFD 自动 PIT/CS 转发均需纳入观察；仅计算 `k−1` 加某个应用函数调用次数不保证完整覆盖。Naive 即使额外副本为零，也不能单独判为最优；Proposed 不能再笼统描述为“只有额外控制报文而绝无额外 Data”。

## 5. 控制报文分类与网络字节口径

### 5.1 以真实协议语义分类

用户最后确认的范围优先于最初三个名称的简写。建议主控制指标采用下列**全部自定义纯控制报文的整包发送长度**，四算法使用相同映射，记录原始 Name 和语义类别。

| 当前代码名称/类别 | 功能 | 主控制 B_ctrl | 网络 B_net |
|---|---|---|---|
| `/vndn/control/hello` Interest 及车辆 Data 响应 | 驻留发现、车辆位置/状态、缓存目录同步 | 包含双方 | 包含 |
| `/vndn/control/p2p-handshake/...` | 基础设施身份发现、响应与传播 | 包含测量窗内全部发送 | 包含 |
| `/vndn/control/rsu-relay/find` | 跨站搜索车辆，功能接近导师 search | 包含 | 包含 |
| `/vndn/control/rsu-relay/found` | 搜索响应，功能接近导师 find | 包含 | 包含 |
| `/vndn/control/neural-route` | 通知 Router 预测回程集合 | 包含 | 包含 |
| `/vndn/control/neural-pit` | 目标 RSU 的 PIT 准备，含编码原 Interest | 包含完整控制包 | 包含 |
| `/vndn/control/rsu-relay/forward` | 外层携带完整原始业务 Data 的补救封装 | **不将整包视为纯控制**；另拆封装开销 | 外层实际发送长度完整计入 |
| 原生业务 Interest/Data、原生 Nack 等 | 基础业务或原生协议机制 | 不属上述自定义纯控制集合 | 按统一统计层计入 |

`forward` 的名称在 `/control` 下，但负载承载业务 Data。为使口径可审计，同时报告：①纯控制 B_ctrl；②混合转发封装的整包字节 B_relay；③其内嵌原始 Data 字节；④两者差值 H_relay（额外封装字节）；⑤可选 `B_ctrl + H_relay` 的控制及封装成本。主图使用①；若导师希望按所有自定义命名前缀整包统计，另提供 `B_ctrl+B_relay`，必须注明含业务载荷，不与①同名混用。

所有字节分解以同一层实际序列化长度和逐跳发送为基础；存在分片时需按完整逻辑消息关联各片，不逐片重复减去整个内嵌 Data。`neural-pit` 虽携带原 Interest，功能是安装回程状态，完整长度计入控制，不能只统计其固定头部。

Naive 仍使用 hello/握手等本项目新增机制，控制负载可能非零。不能给 Naive 人工置零，也不能只画 `Proposed−Naive` 代替所有自定义控制总量。若握手全部发生于预热段，测量段为零须由事件时间证明，预热成本另表保存。

### 5.2 统一发送位置，避免重复与漏计

建议主统计点选 **NDN/NDN-LP 数据块提交网络设备的边界**：每个真实 `netdev` 出口对设备接受的发送记录一次，长度为实际提交的序列化 Block/packet 字节，包含本项目 LP 元数据；覆盖全部 OBU、RSU、Router、Server，排除本地应用 face。底层 `Send` 返回失败另记，不能称其已发送成功。

该层反映协议提交的通信量，**不等于无线信道实际占用**：未包含全部 MAC/PHY 头、MAC 重试、退避或空口时间。若需物理网络成本，另增 MAC Tx 字节/airtime 指标，不把两层数字拼在一起。多跳链路每跳计一次是有意计算资源消耗；无线广播只记一次出口发送，不按听到它的车辆数倍增。

当前 L3RateTracer 的 `Kilobytes` 是平滑速率，`KilobytesRaw` 才是周期内原始 KiB；它没有 Name，不能分出控制子类，且不含完整 LP 标签，Nack 字节还有单独处理。它可作辅助核对，不能直接替代上述统一事件日志。[ndnSIM 指标说明](https://ndnsim.net/2.0/metric.html)

粗略核对 L3 trace 时必须用全部真实网络 face、只取 Out、使用 Raw、完整 flush 尾段，不沿用旧图的 `In+Out`、`Node0–6` 或平滑速率累加。不同统计层的字节不要求数值相等，应按已知编码差异解释。

建议分区核对：`B_net = B_business_interest + B_plain_business_data + B_relay + B_ctrl + B_native_other`。额外副本是业务流量的附加属性，不是再加一遍的字节列。未知控制类型/无法归类的业务副本须显式报告，分类覆盖不完整时不能发布“全部控制”或“全部额外副本”图。

## 6. 随机重复、模型隔离与统计方法

每个 `场景×参数水平×重复编号` 构成一个比较块，四算法共享路线/车辆表、请求计划、移动随机条件和基础配置。固定 ns-3 主 seed，改变 `RngRun` 形成独立重复；每块从预先冻结的列表分配 SUMO seed、C `srand` seed 和请求计划种子，四算法块内一致，不同重复按列表变化。另记录固定模型和分析随机种子。相同 seed 不保证不同协议分支消耗随机数后仍逐项相同，请求/移动应独立控制并核对实际轨迹与请求表哈希；若整组固定移动轨迹，区间只反映该轨迹条件下其他随机性，不能声称覆盖交通移动随机性。[ns-3 随机变量手册](https://www.nsnam.org/docs/manual/html/random-variables.html)、[SUMO 随机性说明](https://sumo.dlr.de/docs/Simulation/Randomness.html)

每场景正式测试前冻结一个 checkpoint、归一化、标签、特征窗口、单双候选阈值及推理配置。训练/验证/预实验/正式测试按完整运行与移动种子隔离；提前说明训练是否覆盖全部速度/车辆水平，不看测试结果再逐点重训。若只评估一个训练种子，结论限定于该固定模型；模型训练随机性的稳健性另做多 checkpoint 补充实验，不混作仿真重复。

建议先做少量独立预实验估计方差和运行成本，再冻结正式重复数 R，例如以 **20 次独立重复作为资源规划起点**，不是充分性的保证。可预先用 ISR 区间宽度、RTT/成本相对精度等目标决定 R；若预算不足，报告区间较宽，不边跑边看显著性后选择停止。

主图点估计与区间建议如下：

1. 每轮先保存 `generated、satisfied、sum_success_rtt、extra_copies、各类bytes` 等充分统计量。ISR、计数、字节主图按 run 等权求均值。
2. RTT 主图使用**成功请求加权均值** `Σrun sum_success_rtt / Σrun satisfied`，明确不同于各 run RTT 均值再等权平均。零成功 run 仍保留在比较块中；某点所有 run 都无成功则 RTT 为 NA。
3. 默认按完整比较块做非参数 bootstrap：有放回抽取 R 个块，四算法共用同一组抽样索引，每次重算均值或 RTT 比值；建议 10000 次重采样、固定分析种子，取 2.5%/97.5% 分位数为点态 95% 区间。不能把同轮几千个包作为几千个独立重复。此处按 run/比较块组织重采样是本方案针对相关包观测的设计；bootstrap 基础见 [Efron 原论文](https://sites.stat.washington.edu/courses/stat527/s13/readings/ann_stat1979.pdf)。
4. 若 RTT 的某些重采样整体无成功，报告其比例，区间标为不可稳定估计，不把这部分重采样静默删除、填 0 或填超时。边界成功率、极稀有副本事件的区间也须检查退化；观察到全零不能自动证明总体发生概率为零。
5. 比较结论使用配对效应量与区间。ISR/计数/字节采用同块差的均值；RTT 使用两算法各自成功请求加权均值的差，并在每次配对重采样中重算，不能只保留双方均有成功的 run 后求差。区间不重叠不是唯一判断规则。点态 95% 区间不等于全部 45 面板的同时覆盖；若开展多重显著性检验，应事先限定主要比较并校正，而非逐点挑显著结果。

若预实验支持近似对称的独立 run 指标，ISR/计数/字节这些按 run 等权平均的指标也可预先改用 t 区间 `mean ± t(0.975,R−1)×s/√R`；不能将各 run RTT 均值的标准差直接套给上述加权比值，也不能在看完优劣后选择更好看的区间方法。区间表征估计不确定性，不是单次观测值的分布范围。[NIST 均值置信区间说明](https://www.itl.nist.gov/div898/handbook/eda/section3/eda352.htm)

## 9. 实施顺序、测试先行与运行规模

1. **先做计数规格测试，再改采集实现。** 用小型确定性事件检验下表口径，先证明旧输出/旧计数不能满足规格，再最小补充。按 [VALIDATION.md](VALIDATION.md) 运行相关回归并记录证据。
2. **构造最小三场景冒烟运行。** 验证车辆在线、全部终态、双路径/跨站复制、事件分类与固定收尾，不能仅看进程 exit 0 或 Gym Done。
3. **独立预实验。** 测量运行时间、数据体积、交接覆盖、实际速度和方差，选择并冻结水平/T/R/请求模式/统计方法；不使用正式测试种子。
4. **正式配对扫描。** 每块保存四算法完整结果和失败记录；排除规则只针对预先定义的基础设施/采集失败，不因协议超时、低 ISR 或高负载删除。重跑保留原失败记录并固定块输入。
5. **统一分析后出图。** 先检查数据闭合，再从同一指标表生成全部 15 图及附表；保存全部点和全部种子，不手选最好的一轮。

| 未来测试例 | 必须成立的断言 |
|---|---|
| 4 请求分别成功、timeout、Nack、停止导致失败 | 生成分母4、成功1、ISR25%；RTT只含成功；停止原因可审计 |
| 同请求两份有效 Data 到车 | 满足数只加1，重复到达可追踪 |
| 一个普通 Data 经过三跳 | 额外副本0，网络发送字节累计三跳，不再加接收端 |
| Router 首次向两目标发送 | 额外副本1；两路字节都进入网络量 |
| 选中两目标但仅一条返回分支被设备接受 | 预测额外副本0；失败尝试单独记录，不能用候选数量代替提交数量 |
| 一次 A→Router→B 跨站补救 | 新副本1；普通中继/解封装不再加；整个外层包各跳计一次 |
| 同副本等待后首次发送，或已发后又被重复发送 | 前者不是新增副本，后者必须进入额外副本分项 |
| hello、neural-pit、含原 Data 的 forward | 前两者完整计控制，后者分为混合业务封装，网络不漏不双计 |
| 最后不足1秒仍有发送/成功收包 | 最终日志包含这些事件，不能依赖周期 tracer 恰好打印 |
| 某 run 无成功、某bootstrap样本无成功 | RTT NA规则及区间不可估计说明正确，禁止补0或静默删样本 |
| 预建PIT自动发无线Data | 统一出口日志可见，不能只在RSU应用发送函数计数 |

若每横轴 5 个水平、四算法、三场景、R=20，直接运行是 `3×3×5×4×20=3600` 轮。若三个扫描共享完全相同基准点，且输入、模型、配置和重复块均相同，可复用基准：每场景 `1+3×(5−1)=13` 个条件，共 **3120 轮**。固定 K 的车辆数补实验在复用共同基准后再增加 `3×4×4×20=960` 轮，总计 **4080 轮**，不含预实验/训练。基准并非完全相同时不得强行合并。

可先用每场景“一个基准＋三个横轴各两个边界”、3 次重复验证可行性，约 `3×7×4×3=252` 轮；更小的冒烟运行先验证采集，不将其当论文样本。最终预算用预实验实测单轮耗时估计，不能把上述轮数误当已经执行的任务。

所有构建和间接触发构建前 `export JOBS=4`；显式构建 `-j 4`，尽可能不运行 `./waf configure`。本方案默认先串行实验避免竞争；后续并行需隔离 gym 与 SUMO 端口、输出和资源，当前 SUMO 端口 3400 写在入口中，还需配置化。当前 Python 控制器一次只服务一轮，批跑必须逐轮管理控制器并验证完成；现有批量 shell 总退出码不足以证明每轮成功。
