## 1. F02：神经方案并非 Circle 四策略中最慢

已逐请求核对 Circle 五负载、四策略、两个种子共 **40轮、252000请求**，20个 F02 柱高全部还原。

| 首次请求数/轮 | Naive NDN | VTDF | RTVTDF | TKAN-PDF |
|---:|---:|---:|---:|---:|
| 1500 | 179.11 | 202.17 | 197.66 | 188.79 |
| 3000 | 180.03 | 210.24 | 205.57 | 196.29 |
| 6000 | 184.46 | 222.80 | 423.08 | 353.52 |
| 9000 | 193.07 | 270.68 | 639.92 | 613.27 |
| 12000 | 230.99 | 429.75 | 665.05 | 659.31 |

单位为 ms。TKAN-PDF 五档的均值均低于 RTVTDF，1500/3000 档也低于 VTDF。真正的问题是从6000档开始明显慢于 VTDF，且高于 Naive。

### 较长延迟出现在哪

对按期成功请求，统计最后一次相关 RSU 无线 L3 Data 提交到目标车辆应用交付的间隔：

| 请求数/轮 | Naive NDN | VTDF | RTVTDF | TKAN-PDF |
|---:|---:|---:|---:|---:|
| 1500 | 16.30 | 32.27 | 32.02 | 25.98 |
| 3000 | 16.52 | 35.48 | 37.83 | 31.71 |
| 6000 | 18.44 | 48.40 | 226.81 | 172.09 |
| 9000 | 23.65 | 88.21 | 443.13 | 424.92 |
| 12000 | 43.48 | 231.86 | 472.34 | 471.37 |

单位 ms。这是无线提交后的交付间隔，包含下层排队、发送、可能的重试、分片/重组等，不是直接测得的纯 MAC 排队时间。

TKAN-PDF 全部成功请求在对应 RSU 收到返回 Data 到无线 L3 提交之间均为0模拟毫秒，主要增加的延迟发生在此后。6000档只比较两策略都成功的相同请求，TKAN-PDF 比 VTDF 慢122.64/121.09 ms，末段差值分别119.15/115.17 ms。因此差距不能全部用“统计的成功请求不同”解释。

F01诊断进一步显示，高负载 TKAN-PDF 提交的无线业务 Data 明显多于 VTDF；VTDF 有不少 Data 被等待逻辑搁置。少做跨站转发、全网字节较少，不等于最后一跳无线更空闲，也不保证每个成功请求更快。

目前证据把差异定位到无线末段，并支持负担/排队压力的解释；尚不能精确分摊排队、重试失败、分片丢失、预测目标站等原因。旧开发小测曾直接观察 MAC 重试与约500 ms队列过期，但属于旧配置旁证，不能把旧数值冒充本批264轮的逐包测量。

### 为什么 Naive 最低，以及为什么不能归因于 Python 推理慢

F02仅计算期限内成功请求的 RTT，不把失败请求填成0或3000 ms。Circle Naive 在五档中只成功约31.5%–35.1%；许多困难请求失败后不进入均值，所以低成功 RTT 不能单独证明其交付效果最好。与此同时，同请求配对仍显示 TKAN-PDF 有真实末段延迟，不能全部归为样本选择。

RTT使用 ns-3 模拟时间。`src/opengym/model/opengym_interface.cc:275` 的同步 ZMQ 收发没有把 Python 现实推理耗时调度成模拟延迟；因此不能将这数百毫秒直接解释为神经模型算得慢。部署计算时延属于另一测量问题。

统计源码：`tools/experiments/summarize.py:263` 核对终态与期限，`:388`计算成功平均；`tools/experiments/aggregate_campaign.py:97`按成功请求数汇总两个种子。固定交接分组不等于“四策略共同成功集合”，本轮相同请求配对另行按请求ID求交集。

## 2. F04：Naive 的 Custom control 是什么

这里的 **Custom 指本项目新增的协议机制，不是仅指神经方案新增的消息**。当前 Naive 是“无回程补救策略”，仍运行 RSU 发现、车辆状态和缓存同步，并非完全未经扩展的原生 NDN。

当前控制集合为：`hello`、`p2p_handshake`、`search`、`find`、`neural_route`、`neural_pit`。其中 hello 包含 RSU 发出的 Interest 和车辆回复的状态 Data。

三场景五档共30轮 Naive，控制字节全部来自 hello；其他控制类别在统计窗口内均为0。以 Circle 6000档、seed23001为例：

- RSU hello Interest：12350次，每次32字节，共395200字节；
- 车辆 hello Data：52959次，平均307.05字节，共16261161字节；
- 合计133.250888 Mbit；另一种子133.099680 Mbit，图中均值133.175284 Mbit。

因此主要成本来自频繁的车辆状态回复，而非只有很小的信标请求。默认20ms周期，即每个RSU约50次/秒；测量和排空成本统一累计20–143.5秒。

神经方案已按用户先前要求单独采用紧凑无损编码、无变化缓存增量省略；其他策略保留旧格式。同条件同种子，神经 hello Data 平均约99.35字节。因此其控制量较低，有一部分是报文编码优化收益，不能全部归因于模型预测。此实现差异保留在方法文档，不改现有图或HTML。

## 3. 控制多、总量较少为什么不矛盾

F04 是 F03 的子集，统一关系为：

`网络总量 = 业务 Interest/Data + 携带业务 Data 的补救封装 + 自定义控制`

`relay_data` 虽有 `/control/` 名称前缀，但携带完整业务 Data，不整包计入纯控制；它完整计入网络总量。字节为网络 Face 的 NDN L3 编码发送量，不含全部 MAC/PHY/重试开销。

Circle 12000档，两种子均值，单位 Mbit：

| 策略 | F04控制 | 业务Interest/Data | 补救封装 | F03总网络量 |
|---|---:|---:|---:|---:|
| Naive NDN | 125.85 | 2751.74 | 0 | 2877.58 |
| TKAN-PDF | 55.57 | 2941.26 | 0 | 2996.83 |

Naive控制多70.28 Mbit，但业务少189.52 Mbit，所以总量仍少119.25 Mbit。Naive控制只占总量约4.37%；6000档约8.25%。F03与F04纵轴量级也不同，不能用两张图中柱子的视觉高度直接比较。

Naive不补救会减少相应开销，但失败请求在前面各跳仍可能产生业务字节，不能简单把“失败多”视为全部流量差别的原因。上表按实际字节分解说明，不用成功率倒推流量。

目前口径符合[论文对比方案](论文对比实验与出图方案.md)第5节：用户后续确认范围为超出原有NDN的自定义控制，因此包含双向hello，并明确Naive不能人工置零。若将来仅研究导师原先的search/find/update，应另命名为回程补救/预测控制，对四策略统一定义；不能只从Naive扣除hello再冒充同一个F04。

当前图集已有 `D05-control-traffic-decomposition.png`（以及SVG/PDF）可查看基准条件控制分项。它与F04的总量相互补充。
