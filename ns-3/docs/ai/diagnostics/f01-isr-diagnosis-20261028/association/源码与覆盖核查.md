# F01：关联源码与几何覆盖核查（2026-10-28）

本核查只读原始输入、已保存 mobility-events.csv 与源码，不扫描 packet-l3.csv，未运行仿真、训练或构建。
数据批次为 `data/experiments/quick-fixed-model-20261022`；80轮为 Grid / Spider 各40轮，即5档Interest × 4策略 × 2种子。
统计脚本 `geometry_audit.py` 执行退出0。结果 `geometry-audit.json` 与 `geometry-per-vehicle.csv` 可复算。
该脚本只说明记录时刻的几何接收必要条件，不是请求成功率估计器，也不是ns-3行为单元测试。

## 已证实的输入与配置

- 每场景同一种子的20轮 SAMPLE 时间、vehicle_id、x、y、speed_mps 排序后SHA-256完全相同；发包数量改变不改变实际移动轨迹。
- 无线速率均为 `OfdmRate6MbpsBW10MHz`，同一频道，共用WifiSetupHelper。7个RSU不意味着7倍无线容量。
- Spider 13dBm / -69.8dBm，Grid 12dBm / -69.8dBm，Circle 10dBm / -78dBm；Spider/Grid前导SNR阈值-4dB，Circle为4dB。
- TwoRayGround默认频率5.15GHz；Helper设置HeightAboveZ=1.5m、SystemLoss=1、MinDistance=50m。
  **小于等于50m时源码直接返回发射功率；超过50m转入传播计算。** 这是现有物理建模的明显分段，不能将源码注释中的“约300m覆盖”当成实际配置。
- RSU坐标从settings.xml读取，Z统一12m；OBU由TraCI设置Z=1.5m。Tx/RxGain默认为0dB。
- 在这些配置下，距离小于交叉距离，阈值采用Friis分支；Grid水平灵敏度必要半径约56.015m，Spider约63.077m。
  在半径内仍可能因干扰、碰撞、队列、解码、协议而失败；半径不是“可靠覆盖范围”。
- RadioHelper、传播、TraCI不在旧source.tar.gz范围内；本次按80轮运行manifest中实际出现的git版本逐一核对，
  包括`c258be6c0cc165d5f3e99ff264cd56da1de2f256`与`c64023a4af55b0f47fa01898a1a86352aae28889`，四文件内容均一致。
  不以同git revision代替封存源码身份，原source.sha256也分别记录。场景入口、RSU坐标解析、Grid/Spider settings与封存tar逐字一致。
  这是按所记源码与配置重建，不宣称重新检验历史动态链接库内部参数。

## 记录位置的覆盖结果

测量窗口20–140s，每车1200个0.1s SAMPLE，共12000个车辆时刻。只计至少一站的理论接收功率达到灵敏度。

| 场景 | seed | 满足几何必要条件比例 |
|---|---|---:|
| Grid | 23009 | 93.3500% |
| Grid | 23010 | 94.1917% |
| Spider | 23017 | 60.6417% |
| Spider | 23018 | 52.6250% |

该比例跨5档负载、四策略相同；Spider平均约56.63%，与已观察约56%的业务满足率在量级上吻合。
这不是严格ISR上界，原因包括采样时刻不同于请求时刻、车辆移动、Data缓冲与超时窗口。

具体反例：Spider seed23018 的 exp-00001 在0.020192070s首次驻留RSU5；到结束仍记录5。
但测量窗口内最近任意RSU的水平距离都在74.811–106.731m，超过63.077m必要半径，
1200个样本中没有任何基站满足灵敏度。轨迹在四种策略相同；因此不能把这辆车的全失败
直接归因于“没有换到另一个可达基站”。它在测量窗口走的是无线盲区，旧RSU过期清理也不能创造覆盖。

Spider40轮中，每轮“当前RSU不满足灵敏度，但其他RSU满足”的样本最多26/12000=0.217%；
Grid40轮最多149/12000=1.242%。该分类不判定实际可达，也未覆盖所有关联决策缺陷；只能排除其为Spider大量失败的唯一解释。

## 已证实的源码边界

1. `contrib/vndn-nn-rd/apps/vndn-obu.cc:134–190`：只在收到有VndnTag的hello时更新/清理邻居。
   超时判断为当前毫秒与lastUpdateMs之差>2000，见h:270。无hello时没有独立清理事件。
2. `vndn-obu.cc:446–474`：发包选择旧currentBs对应senderMac，只检查记录存在与非零MAC，不查新鲜度。
   `vndn-obu.cc:267–285`取候选NextRsu时依赖同一个已经清理过的map。
   因此“丢失所有hello后继续使用旧邻居记录”的逻辑缺口可由代码证明。
3. `vndn-obu.cc:202–249`：只有新站RSS严格大于当前站存储RSS才切换，或当前站已经清空。
   由于50m内功率平台，不能假设地理最近站一定立即成为关联站；同一RSU ID持续不变不等于信息陈旧。
4. `scratch/vndn-map-simulator-common.h:374–413`：SUMO车辆进场才安装OBU；出场StopApplication并关闭WifiPhy。
   当前审计80轮均有完整测量窗口的每车1200样本，整车始终失败不是中途退出/关闭造成。
5. `scratch/vndn-map-simulator-common.h:329–336,455–457`：每站P2P直连一个Router，均有到Router的默认FIB，Router连接Server。
   拓扑不是只有某个RSU有回程；具体报文是否沿路径到达须由包表审计，不从配置断言。

## hello可观测性限制

- `contrib/vndn-nn-rd/helper/vndn-l3-experiment-tracer.cc:60–65`仅订阅OutInterests、OutData、OutNack与InData。
  `ReceivedData:107–112`只记录业务前缀；原packet-l3.csv没有任何hello入站行。
- OBU出站hello DATA是应用处理过当前驻留站hello的肯定证据；其不存在不能反证未收过其他站hello，
  因为OBU对不切换的非驻留hello只更新邻居后return（obu.cc:247–251）。
- 即使以后补L3 InInterests，仍需区分Face接收与应用处理：forwarder.cpp:126–157还存在Nonce/DNL/PIT重复路径；
  multicast策略仅跳过控制Interest的上游重传抑制，并未绕过所有forwarder检验。
  要准确量化陈旧关联的危害，应直接记录应用层hello接收/清理事件、发包时lastUpdateMs和selected RSU/MAC，不能拿OUT时间冒充接收时间。

## 后续修改建议（尚未实施）

- 关联新鲜度修复作为共享协议正确性工作：测试“无hello超过阈值”“刚过阈值边界”“新站首次hello”“正常持续hello”“停止取消事件”；
  选择一个独立清理调度，或在发送/读关联前集中清理并准确记录离线事件。各策略同规则，不能只让某个算法额外丢包。
- 记录新鲜度与包生命周期的小规模工程样本，先证明修复减少了确切的错误目标发送。不能预先承诺ISR改善，更不能声称能恢复物理盲区。
- 若研究重点要隔离“有覆盖情况下的基站交接”，另列全策略统一的新场景：减少道路盲区、保持交接覆盖与既定请求定义；
  固定参数前先检查几何和实际链路。不可仅为使TKAN-PDF高于VTDF调整发射功率/删掉车辆或失败记录。
- Radio MinDistance=50m的功率突变及传播频率与Wifi频道设置的区别值得单独审查，但不是本次只读排查中自动修改的范围。
