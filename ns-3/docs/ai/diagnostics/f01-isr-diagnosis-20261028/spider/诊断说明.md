# Spider F01 低高请求负载的只读漏斗核查（2026-10-28）

本证据只分析 `quick-fixed-model-20261022` 的 Spider、1500/12000 请求、
23017/23018 两个 seed、四策略，共16个已完成旧运行。不运行仿真，不修改正式源码、图或原数据。
每轮固定10车、30 km/h设置、20–140 s测量。不同档实际请求量为1500/12000，全部有OBU Interest网络出站。

## 复算

在 ns-3 根目录执行：

```bash
python3.8 build/validation/f01-isr-diagnosis-20261028/spider/diagnose_saved_spider.py
```

脚本流式读取packet CSV，生成本目录下JSON与三张CSV。实际执行退出码0。
80个输入文件均与原run manifest的artifact_hashes匹配；读取前后SHA256一致。
每轮生成量/满足量与保存的run-details.json一致。所有阶段集合包含关系检查结果为0例逆序。

- `spider-funnel.json`：逐轮唯一请求漏斗、包事件数、失败层、数据哈希与定义限制。
- `run-funnel.csv`：16轮的漏斗汇总。
- `vehicle-funnel.csv`：逐轮逐车，160行，含hello响应、关联变化、请求阶段及位置范围。
- `time-bin-funnel.csv`：逐轮10秒窗口，192行。
- `analysis.log`：实际运行输出。

## 典型整车失败

seed23018的 `exp-00001`（节点8）在四策略、两个请求档均出现：

- 150/1200次GENERATED、150/1200次OBU Interest OUT；后续RSU上行、服务器Data、RSU Data入口/出口、目标OBU收包、应用满足全为0。
- 测量窗口20–140s内hello响应Data OUT为0，无关联变化；最后关联记录在0.020192070s，RSU5。
- 车辆并未静止在同一位置：测量轨迹 x范围约4.02–274.68m，y范围约6.20–344.81m，关联字段仍保留5。

因此 `rsu_id >= 0` 不能当作有效无线覆盖或新鲜关联证据。
神经方案两档共3000/24000请求中，生成时rsu_id=-1仅112/910（3.73%/3.79%），
仅按负rsu_id计“失联请求”会漏掉大量长期保留旧站编号的失败。

为避免20s采集起点造成左删失，hello最近2秒统计只覆盖发送时刻>=22s的请求。
神经低/高档有1256/10055个请求在前2秒没有观察到OBU hello响应，全部失败，
约占该档全部失败的95.88%/95.17%。这是响应缺失与失败的强关联，不能当作完整物理收包因果证明。

## 代码中的独立待核查点

`contrib/vndn-nn-rd/apps/vndn-obu.cc:175` 邻居过期清理位于收到新hello的处理函数内；
`vndn-obu.h:270` 默认阈值2000ms。
`vndn-obu.cc:467` 发业务Interest仅检查旧邻居条目存在和MAC非0，没有直接检查lastUpdateMs新鲜度。
若不再收到hello，旧条目可能长期保留，并可能继续选择旧站MAC。
该公共行为影响全部四策略。旧CSV未保存发送目标MAC，不能据本证据声称逐请求已核实发送到了旧MAC。

## 记录边界

- `packet-l3.csv` 只有OUT方向；本次RSU上行Interest OUT是收到并转发的代理证据，不能命名为RSU Interest RX。
- `data-rx.csv` 为完整网络Data入口；这与应用按期成功分开计数。
- VTDF高档有54/18个失败请求其实后来收到了完整Data，首次完整收包均晚于3秒deadline：seed23017为8.18–86.71秒，seed23018为3.24–42.90秒。
- 没有逐hello入口、目标MAC、无线丢包原因或MAC重试日志；simulation.log以`--log=0`运行，仅约3KB。
- RSU无线face=257由该批次simulation.log的netdev face映射及拓扑建立代码确认；RSU0–6、OBU7–16、Router17、Server18。
- 原图数据和数值均未更改。若修复公共关联机制，必须共同作用于四策略、另跑新批次，不能拿新旧混合数据拼比较图。
